# Spec: MDA-1 — Registro de MDA (Tendências da População)

## Status
Proposta

## Resumo
Permite ao jogador registrar um **MDA** (Mass Data Analysis) — um card de referência persistente que captura a **tendência da população** (exploit do field) num spot de poker, com prints das stats da população, tagueado a **vários temas (N:N)**, consultável enquanto estuda qualquer tema tagueado.

## Contexto
Hoje o registro de estudos suporta `stat_analysis` (EST-3, migration 0087): minha-jogada-vs-GTO, **sessão cronometrada**, ligada a **1 tema**. Falta um artefato distinto e complementar:

- `stat_analysis` = minha jogada vs GTO, **sessão**, 1 tema, com tempo/XP.
- **MDA** = exploit da população, **card de referência (sem tempo/XP)**, **N temas (N:N)**, consultável durante o estudo.

MDA é **irmão** do `stat_analysis`: reusa a máquina de imagem/validação (storage privado, magic-bytes, validação de statId), mas tem **tabela e rotas próprias** (não é `mode` em `study_sessions_v2`).

Valor central: registrar um MDA uma vez (spot + filtros + tendência + prints + stat opcional), tagear a N temas, e ver os MDAs relevantes da população ao estudar qualquer desses temas.

## Decisões Travadas (NÃO reabrir)
1. **Tagging N:N** — tabela dedicada `mda_reads` + junction `mda_read_themes`.
2. **Card de referência** — sem duração/XP. NÃO é `mode` em `study_sessions_v2`. Tabela própria.
3. **Campos por MDA**: title, spot/contexto, filtros aplicados, tendência/exploit, stat ligada (opcional), prints (vários, cap 8).
4. **Tier gate**: MDA é estudo core → **sem gate** (paridade com `stat_analysis`, que não gateia).

## Usuários
- **Jogador MTT (autenticado)**: registra, edita, consulta e exclui seus próprios MDAs. Consome MDAs ao abrir um tema ou estudar.

## Fora de Escopo (Deferidos)
- Biblioteca global `/estudos/mda` + busca global de MDAs — fase 2 (MVP entrega via tema + painel de estudo). O endpoint `GET /api/mda-reads` paginado é **opcional**; se não implementado, não bloqueia o sprint.
- Ligar MDA a `starred_hands` (spot estruturado) além de texto livre — fase 2.
- Coach / mentor surfacing de MDAs no chat ou relatório — candidato futuro.
- Tier gate (default OFF nesta sprint).
- Ownership check de `statId custom_*` — herda o mesmo TODO grepável do EST-3 (MEDIUM-1); `custom_*` validado só por shape.

### RF-02: Backend Storage (`server/storage.ts`)
**Descrição:** Camada de acesso a dados para MDA (CRUD + diff de tags idempotente + CRUD de imagens jsonb), exposta via `(storage as any).x`.

**Regras de negócio:**
- `createMdaRead(input)` — insere read + tags. Transação se `db.transaction` disponível, **fallback gentil** (lesson #32 — detection `typeof db.transaction === 'function'`). Normaliza `images` (gera `id` via `nanoid()` se faltar).
- `getMdaReadById(id, userId)` — read + `themeIds` (JOIN junction), `deleted_at IS NULL`. Retorna `null` se não existe ou outro user.
- `getMdaReadsByTheme(userId, themeId)` — JOIN junction filtrado por `(user_id, theme_id)`, agrupa, retorna reads com keys **crus** (handler mapeia URLs). Exclui `deleted_at IS NOT NULL`.
- `updateMdaRead(id, userId, patch)` — merge de campos + **diff de tags** (append novos / remove ausentes, UNIQUE-aware; espelha `appendStatToThemes`/`removeStatFromThemes` lesson #33 — append idempotente via `@>`, remove via `jsonb_agg`/delete na junction).
- `addMdaReadImage(id, userId, image)` / `removeMdaReadImage(id, userId, imageId)` — CRUD do array `images` jsonb. `removeMdaReadImage` retorna `oldKey` p/ cleanup.
- `getMdaReadImageKey(id, userId, imageId)` — retorna key cru p/ serve (com ownership).
- `softDeleteMdaRead(id, userId)` — set `deleted_at`, retorna keys p/ cleanup best-effort.
- `deleteTheme` (storage **existente**, alteração): após deletar o tema, `DELETE FROM mda_read_themes WHERE theme_id=? AND user_id=?` (cleanup de tags órfãs — sem FK).

**Critério de aceitação:**
- [ ] `createMdaRead` com `themeIds:['t1','t2']` cria 1 read + 2 rows na junction.
- [ ] `createMdaRead` normaliza `images` sem `id` gerando `id` via `nanoid()`.
- [ ] `getMdaReadsByTheme(user,'t1')` retorna o read; `getMdaReadsByTheme(user,'t2')` também (mesmo read em 2 temas).
- [ ] `updateMdaRead` com `themeIds:['t2']` (era `['t1','t2']`) **remove** a tag `t1`, **mantém** `t2`.
- [ ] `updateMdaRead` re-aplicar mesmas tags é **idempotente** (UNIQUE não duplica).
- [ ] `softDeleteMdaRead` faz o read sumir de `getMdaReadById`/`getMdaReadsByTheme` e retorna as keys.
- [ ] `deleteTheme(user,'t1')` remove rows de `mda_read_themes` com `theme_id='t1'`; read sobrevive se ainda tagueado a `t2`.
- [ ] `createMdaRead` usa fallback gentil quando `db.transaction` indisponível (lesson #32).

### RF-03: Rotas `/api/mda-reads/*` (`server/routes/mda.ts`)
**Descrição:** Novo módulo `registerMdaRoutes(app)`, namespace `/api/mda-reads`. Todos handlers no padrão `handleX(req, res, injectedStorage?)` com lazy `await import('../storage')` em prod (lesson #34). Validação Zod **antes** de I/O.

**Regras de negócio:**
- Sub-paths de imagem (`/:id/images/...`) registrados **ANTES** do `:id` genérico no módulo (hábito anti-colisão; namespace já evita colisão com legacy `study-sessions/:id`, mas manter o hábito). Guard test dedicado `tests/integration/routes/mda-route-collision.test.ts` (espelha est-3).
- Todas as rotas exigem `requireAuth`. Ownership validado por `userId` em toda query.
- POST/PATCH validam ownership dos `themeIds` (temas pertencem ao user) + `statId` (`isValidStatId`).
- Registro em `server/routes/index.ts`: `registerMdaRoutes(app)`.

**Endpoints Previstos:**
| Método | Rota | Descrição | Auth |
|---|---|---|---|
| POST | `/api/mda-reads` | cria read + insere tags (valida ownership temas + statId) | requireAuth |
| GET | `/api/mda-reads/by-theme?themeId=` | lista reads tagueados ao tema (keys→URLs) | requireAuth |
| GET | `/api/mda-reads/:id/images/:imageId` | serve print privado (ownership via read) | requireAuth |
| POST | `/api/mda-reads/:id/images` | upload print (multipart `file`, multer mem 5MB, magic-bytes PNG/JPEG/WebP, rate limit) → `{id,url}` | requireAuth |
| DELETE | `/api/mda-reads/:id/images/:imageId` | remove print (best-effort delete storage) | requireAuth |
| GET | `/api/mda-reads/:id` | detalhe (campos + URLs imagens + themeIds) | requireAuth |
| PATCH | `/api/mda-reads/:id` | edita campos + re-tagueia temas (diff) | requireAuth |
| DELETE | `/api/mda-reads/:id` | soft delete + best-effort delete prints | requireAuth |
| GET | `/api/mda-reads` (opcional) | biblioteca paginada de todos MDAs do user | requireAuth |

**Critério de aceitação:**
- [ ] POST `/api/mda-reads` com payload válido retorna `201`/`200` com `id` + read criado; tags inseridas.
- [ ] POST com `themeIds:[]` retorna `400` (Zod min 1).
- [ ] POST com `themeId` de outro user retorna `403`/`400` (ownership de tema).
- [ ] POST com `statId` inválido (não catalog, não `custom_*`) retorna `400`.
- [ ] GET `/api/mda-reads/by-theme?themeId=t1` retorna os reads do tema com URLs de imagem (não keys cruas).
- [ ] GET `/api/mda-reads/by-theme` sem `themeId` retorna `400`.
- [ ] GET `/api/mda-reads/:id` de read de **outro user** retorna `404`.
- [ ] PATCH `/api/mda-reads/:id` re-tagueia (remove `t1`, mantém `t2`) e edita campos.
- [ ] DELETE `/api/mda-reads/:id` faz soft delete; GET subsequente retorna `404`.
- [ ] Guard test confirma que sub-paths `/:id/images/...` não são shadow-eados pelo `:id` genérico.
- [ ] Handlers aceitam `injectedStorage` como 3º arg (lesson #34); em prod fazem lazy import.

**Critério de aceitação:**

## Requisitos Não-Funcionais
- **Segurança:** prints em storage **privado** (`private-uploads/mda/...`), nunca público (copyright). Serve só com `requireAuth` + ownership. Cross-user retorna `404` (não vaza existência).
- **Validação:** Zod `.parse()` antes de qualquer I/O. Magic-bytes para imagem (não confiar em extensão/MIME do client).
- **Idempotência:** tagging via UNIQUE `(mda_read_id, theme_id)`; re-aplicar tag não duplica.
- **Robustez:** `db.transaction` com fallback gentil quando indisponível (lesson #32). Cleanup de storage best-effort (delete que falha não derruba a operação principal).
- **Performance:** índice `(user_id, theme_id)` na junction (query "por tema" é a quente, chamada por ThemeDetailView + painel de estudo).

## Cenários de Teste Derivados

### Happy Path
- [ ] Registrar MDA com 2 prints + 2 temas + stat opcional → salva, aparece nos 2 temas.
- [ ] Consultar `by-theme` num tema retorna o read com URLs de imagem.

### Validação de Input
- [ ] `themeIds:[]` → rejeitado (Zod min 1) no schema e na rota (`400`).
- [ ] `themeIds` com 21 itens → rejeitado (max 20).
- [ ] 9 imagens / 9º upload → rejeitado (cap 8).
- [ ] `title` ausente → rejeitado.
- [ ] `tendencyText` > 2000 / `filters` > 500 / `spotContext` > 200 / `caption` > 120 → rejeitado.
- [ ] `statId` que não é catalog nem `custom_*` → rejeitado.
- [ ] Upload com magic-byte inválido (extensão falsa) → `400`.
- [ ] Upload > 5MB → rejeitado.

### Regras de Negócio (N:N tagging)
- [ ] Card aparece nos **N temas** tagueados.
- [ ] PATCH removendo 1 tag → card **some daquele tema, fica no outro**.
- [ ] Deletar tema → tag órfã é limpa; o read **sobrevive** se ainda tagueado a outro tema.
- [ ] Re-aplicar a mesma tag (PATCH idempotente) → não duplica (UNIQUE).
- [ ] `statId custom_*` aceito por shape; catalog id validado via `getStatById`.

### Edge Cases
- [ ] Imagem privada: `200` com auth do dono; `404` cross-user.
- [ ] GET/PATCH/DELETE de read de outro user → `404`.
- [ ] Soft delete: read some das queries mas a row persiste (`deleted_at` setado); keys retornadas p/ cleanup.
- [ ] `db.transaction` indisponível → `createMdaRead` usa fallback gentil sem quebrar (lesson #32).
- [ ] DELETE de print cujo storage delete falha → operação principal não falha (best-effort).
- [ ] Guard de colisão de rota: `/:id/images/:imageId` não é shadow-eado pelo `:id` genérico.
