## Resumo
Terceiro e último sprint da Fase 1 do plano de melhoria dos agentes de IA. ### Discrepância de plano a corrigir (importante — base do tier gating estrito, RF-03)
**`users.subscriptionPlan`** é `'trial' | 'active' | 'expired' | 'admin'` (schema linha ~51) — **NUNCA** `'pro'`/`'premium'`. A distinção pro/premium vem de `user_subscriptions` JOIN `subscription_plans.name` via `resolveUserTier(user)` em `server/coachAccess.ts` (retorna `'free' | 'pro' | 'premium' | 'admin'`; `'trial'`/`'expired'`/`''` → `'free'`; `'active'` → consulta `user_subscriptions`; cache TTL 30s + promise-cache anti-thundering-herd; `clearUserTierCache(userId)` para invalidar). **O AI-1B introduziu um bug latente:** `PRO_PLANS = new Set(['pro','premium','admin'])` em `reportJobRunner.ts` + filtro `listUsersForCron("subscription_plan IN ('pro','premium')")` — como `users.subscription_plan` nunca contém `'pro'`/`'premium'`, esse filtro **só pega `admin`** (e o `getUserSubscriptionPlan` do `reportStorage.ts` lê `users.subscriptionPlan` cru, então retorna `'trial'`/`'active'`/etc, que `PRO_PLANS` rejeita). Resultado: hoje **nenhum user real recebe o Weekly Report** exceto admin. **AI-1C deve corrigir isso** (RF-03) — usar `resolveUserTier` (ou um `getReportTierForUser`) como a fonte canônica de tier para elegibilidade de relatório, em vez do filtro de `subscription_plan` cru. Esse fix é parte do escopo (não é "fora de escopo" — o tier gating estrito é justamente isso).

### RF-02: Tier gating estrito — quem recebe qual relatório, fonte canônica de tier, downgrade
**Descrição:** Formalizar e corrigir o gating. Tabela de elegibilidade (vale para Weekly do AI-1B + Daily + Monthly deste sprint):

| Plano (`resolveUserTier`) | Daily Debrief | Weekly Report | Monthly Report | Como |
|---|---|---|---|---|
| `free` | ❌ nunca | ❌ nunca | ❌ nunca | toggles não aparecem na UI; enqueuer/gerador revalidam e não enfileiram/skipam |
| `trial` (= `users.subscription_plan='trial'`) | ✅ opt-in | ✅ opt-in | ✅ opt-in | toggles aparecem; opt-in default false |
| `pro` (`active` + plano "pro" em `user_subscriptions`) | ✅ opt-in | ✅ opt-in | ✅ opt-in | idem |
| `premium` (`active` + plano "premium") | ✅ opt-in | ✅ opt-in | ✅ opt-in | idem |
| `admin` | ✅ opt-in | ✅ opt-in | ✅ opt-in | idem (mas opt-in default false — admin precisa ligar) |

- **Fonte canônica de tier:** `resolveUserTier(user)` de `server/coachAccess.ts` (mapeia `users.subscriptionPlan` + `role` + `user_subscriptions` → `'free'|'pro'|'premium'|'admin'`; `'trial'`/`'expired'`/`''` → hoje retorna `'free'`). **Mudança necessária:** a noção de "tier elegível para relatório" inclui Trial. Decisão: criar um helper `getReportTier(user): 'free' | 'eligible'` (ou `isReportEligibleTier(user): boolean`) em `coachAccess.ts` (ou num módulo `server/coach/reportTier.ts`) que retorna `eligible` quando `subscriptionPlan === 'trial'` OU `resolveUserTier(user) ∈ {'pro','premium','admin'}`, e `free` caso contrário. **Não** mudar o comportamento de `resolveUserTier` em si (ele gateia rate limit e tools — Trial → free lá, mantém). O `REPORT_ELIGIBLE_TIERS`/`getReportTier` é um conceito separado, só para relatórios.
  - **Implicação no enqueuer/cron:** `listUsersForCron` hoje filtra por `users.subscription_plan IN (...)`. Como precisamos de `'trial'` + (`'active'` que vira pro/premium via JOIN), opções: (a) `listUsersForCron("subscription_plan IN ('trial','active','admin')")` para ter o candidate set + para cada candidate `'active'` chamar `resolveUserTier` para confirmar que é pro/premium (não free); (b) um método novo `storage.listUsersEligibleForReports()` que faz o JOIN. **Recomendação:** opção (a) — reusa `listUsersForCron`, e o `resolveUserTier` tem cache; system-architect decide. O critério: o enqueuer só enfileira para users cujo tier é elegível (não free) E que tem o opt-in ligado.
  - **Helper de elegibilidade por tipo:** `isReportEligible(userId, reportType: 'weekly'|'daily'|'monthly'): Promise<boolean>` = `getReportTier !== 'free'` && `prefs[report{Weekly|Daily|Monthly}Enabled] === true`. Safe-deny em erro de leitura (lesson #9). O AI-1B `isWeeklyReportEligible` é refatorado para delegar a esse helper (corrigindo o `PRO_PLANS` bug — agora Trial passa).
- **Revalidação no processamento (downgrade):** o processor do AI-1B já revalida (`revalidateEligibility` em `reportJobRunner.ts`). Atualizar para usar `getReportTier` (em vez de `PRO_PLANS.has(snapshot)`) — se o user fez downgrade para free ou desligou o opt-in entre enfileirar e processar → `status='skipped'`, `last_error='no_longer_eligible'`, nenhum `reports` row. Funciona para weekly/daily/monthly.
- **Snapshot de plano:** `report_jobs.subscription_plan_at_enqueue` continua sendo o snapshot de `users.subscription_plan` (auditoria); a elegibilidade real é revalidada no processamento via `getReportTier`.
- **`reportStorage.getUserSubscriptionPlan`:** já lê `users.subscriptionPlan` cru via `getUserById` (WHERE `user_platform_id`). Mantém — mas o `revalidateEligibility` não deve mais comparar isso direto contra `PRO_PLANS`; deve passar pelo `getReportTier`.

**Critério de aceitação:**
- [ ] `getReportTier(user)` (ou `isReportEligibleTier`) retorna `'free'` para `subscriptionPlan ∈ {'free','expired',''}` sem subscription ativa; retorna elegível para `'trial'`, para `'active'` com plano pro/premium em `user_subscriptions`, e para `'admin'`/`role='admin'`.
- [ ] `isReportEligible(userId, 'weekly'|'daily'|'monthly')` = elegível-de-tier && opt-in-do-tipo-ligado; `false` para Free com opt-in `true`; `false` em erro de leitura (safe-deny).
- [ ] O enqueuer (weekly do AI-1B + daily + monthly) só enfileira para users elegíveis (não free) com o opt-in do tipo ligado — verificável: user `trial` com `reportWeeklyEnabled=true` agora recebe job (antes não recebia por causa do `PRO_PLANS` bug); user `free` com `reportDailyEnabled=true` não recebe.
- [ ] `revalidateEligibility` no processor usa `getReportTier` — user que fez downgrade para free entre enfileirar e processar → job `skipped`, sem `reports` row; user que desligou o opt-in → idem.
- [ ] A UI de Preferências mostra os 3 toggles (weekly/daily/monthly) só para tier elegível; Free vê uma linha desabilitada ("disponível no plano Pro" ou Trial) ou nada — o toggle funcional não aparece para Free.
- [ ] Documentado no ADR: o `PRO_PLANS` cru do AI-1B foi corrigido — relatórios elegem por `getReportTier`, não por `users.subscription_plan` direto.

### RF-03: Daily Debrief — schema do job, gatilho (event-driven pós-`session.completed`), conteúdo, custo, fail-soft, cap diário
**Descrição:** Relatório curto e barato gerado depois que o jogador finaliza uma sessão de grind no `/grind-live`. Opt-in (`report_daily_enabled`), só tier elegível.

#### RF-03.1 — Gatilho (event-driven)
- **Onde:** `server/routes/grind-sessions.ts` → `handleUpdateGrindSession` (PUT `/api/grind-sessions/:id`), no bloco que hoje roda quando `req.body.status === 'completed'` (logo após `stopService.evaluateStops`). **Não existe event bus formal** — plugar diretamente, **best-effort**: um helper `enqueueDailyDebriefForSession({ userId, sessionId, now })` chamado dentro de um `try/catch` que **nunca** lança e **nunca** atrasa a resposta (a resposta do PUT deve sair imediatamente; o enqueue é fire-and-forget — pode ser `void enqueueDailyDebriefForSession(...).catch(...)` sem `await`, ou um `await` rápido que só insere uma row). **NÃO gera o relatório síncrono** — só enfileira um `report_jobs` row; o processor do AI-1B (que já roda a cada 15min) gera depois.
- **O que o enqueue faz:** (1) revalida `isReportEligible(userId, 'daily')` (tier elegível + opt-in) — se não, no-op; (2) checa o **cap diário** (RF-03.5) — se já tem um daily job/report pra esse user hoje, no-op (ou agrupa — ver RF-03.5); (3) calcula `period_start` = a **data da sessão** (`completedAt` no fuso do user, formato `YYYY-MM-DD`), `period_end` = a mesma data (debrief cobre 1 sessão de 1 dia; se houver várias sessões no mesmo dia → ver RF-03.5); (4) `INSERT INTO report_jobs (...) ON CONFLICT (user_id, report_type, period_start) DO NOTHING` com `report_type='daily'`, `period_start = data`, `period_end = data`, `scheduled_for = now` (processa no próximo tick do processor), `status='pending'`, `timezone = user.timezone`, `subscription_plan_at_enqueue = user.subscriptionPlan`, `enqueued_by = 'session_completed'`, e — **importante** — uma referência à sessão (o `report_jobs` schema não tem campo `session_id`; opções: (a) gravar `sessionId` dentro de um campo de metadados — não tem; (b) o gerador do daily, ao processar, busca a(s) sessão(ões) do dia via `getGrindSessions(userId, ...)` filtrando por data — **recomendado**, não precisa de coluna nova; (c) adicionar `report_jobs.context_ref text` na migração 0068 — só se o system-architect achar necessário). **Recomendação: opção (b)** — sem coluna nova; o gerador deriva a(s) sessão(ões) do dia pelo `period_start`.
- **Idempotência:** UNIQUE `(user_id, 'daily', period_start)` garante 1 daily job por user por dia. Se o jogador finaliza 2 sessões no mesmo dia, o 2º enqueue é no-op (ON CONFLICT DO NOTHING) — mas o gerador, ao processar, agrega **todas** as sessões do dia (RF-03.5). Se quiser regenerar (raro), o processor já trata via `getReportForPeriod`.

#### RF-03.3 — Conteúdo (seções curtas)
O daily debrief é **curto** (~$0.013). Seções:
1. **Cabeçalho** — "Sua sessão de DD/mês — Xh, N torneios, +$Y (ROI Z%). [comparação curta vs suas últimas sessões: 'acima/abaixo do seu ritmo recente']." Tom = `tomPreferido`.
2. **Resultado da sessão** — torneios jogados / ITM / FTs / cravadas / lucro por moeda nativa + USD; ROI da sessão.
3. **Spots e notas** — "Você registrou N spots/notas. [1 destaque, se houver]." Se 0 → "Nenhum spot registrado — vale revisar prints na próxima."
4. **Comparação com a média recente** — 1-2 frases (data-grounded, com `[fonte: ...]`).
5. **Feedback acionável** — 1-2 pontos (LLM, data-grounded, com citação). Ex: "ROI -12% essa sessão (n=8) — não tira conclusão de 8 torneios, mas se repetir vale olhar selection." Confidence tag quando a amostra é pequena (sessão isolada → quase sempre `low`).
6. **Sugestão (opcional, no máximo 1)** — pode ser link (`/estudos`, `/biblioteca`, `/grade-planner` via `/coach`, `/bankroll`) ou referência a uma tool que existe (AI-0A — `log_leak_focus`, `verify_leak_progress`, `register_tournament_in_grade`, `log_study_session`). **NUNCA** tools AI-2A/2B.
7. **Seção "Seu acompanhamento"** (RF-08) — só se houver foco de leak ativo ou meta em progresso: 1-2 linhas fechando o loop ("Seu foco do mês ainda é X — a sessão de hoje teve dado relevante? Atualize seus stats."). Se nada ativo → omitida.

#### RF-03.4 — Custo / modelo / fail-soft
- Modelo: `process.env.COACH_MODEL ?? 'claude-sonnet-4-6'` (mesma fonte canônica do AI-1B — usar a constante do projeto, não hardcodar string solta; verificar `coachSystemBuilder.ts` / ADR-021). `max_tokens` baixo (~1200 — é curto). Custo estimado ~$0.013/debrief — calcular do `usage`, gravar em `reports.cost_usd_estimate` + tokens. Prompt único `server/coach/prompts/dailyDebrief.ts` (lesson #10 — reusa `GRINDFY_AI_BASE` + `CITATIONS_RULES`; `cache_control: { type: 'ephemeral' }` nos blocos estáveis).
- **Bundle pequeno** — sumarização hierárquica (RF-07) **não** é acionada para o daily (1 sessão = bundle pequeno; o threshold de tamanho não dispara). `summarizer_model_used = null`.
- **Fail-soft:** mesmo padrão do AI-1B (`new AnthropicCtor` em try/catch — lesson #5/#35; sem `ANTHROPIC_API_KEY` → determinístico, `degraded_reason='no_anthropic_key'`, job `done` na 1ª tentativa; LLM falha 3x → determinístico, `degraded_reason='llm_failed_3x'`, job `done` nunca `failed`; erros logados antes do fallback — lesson #9). Determinístico = seções 1-3 com os números, sem `narrative`/feedback de prosa, `cta` só links.
- **`dataSufficiency`:** se a sessão tem 0 torneios e 0 spots → daily minimalista (`status='ready'`, `dataSufficiency='low'`, header tipo "Sessão registrada sem torneios — tudo certo?"). Custo ≈ 0.

#### RF-03.5 — Cap diário / múltiplas sessões no mesmo dia
- **Risco:** Daily é barato mas frequente — um grinder pode finalizar 2-3 sessões/dia. Decisão: **1 daily debrief por user por dia** (a UNIQUE `(user_id, 'daily', period_start=data)` já garante isso). Se o jogador finaliza a 2ª sessão, o enqueue é no-op (job já existe); quando o processor roda, o gerador **agrega todas as sessões do dia** (não só a 1ª). Resultado: o daily debrief é sempre "sua(s) sessão(ões) de hoje". (Se a 1ª sessão já foi processada e gerou o report, e depois vem a 2ª — opção: (a) deixar o report da 1ª como está [o daily cobre "o que tinha quando processou"]; (b) o 2º enqueue, vendo que já existe report, marca o job pra regerar — `INSERT ... ON CONFLICT DO UPDATE SET status='pending', updated_at=now` no `report_jobs`, e o processor regerar pegando o `getReportForPeriod` e fazendo UPSERT no `reports`. **Recomendação: (b) com regen** — o report da última hora reflete o dia inteiro; mas o system-architect pode escolher (a) por simplicidade. Critério mínimo: nunca mais de 1 daily report por user por dia, e o conteúdo cobre as sessões do dia que existiam quando processou.)
- **Cap absoluto adicional (defesa):** mesmo com a UNIQUE, o helper `enqueueDailyDebriefForSession` faz um pré-check barato (`getReportForPeriod(userId, 'daily', hoje)` ou `count report_jobs WHERE user_id=? AND report_type='daily' AND period_start=hoje`) — só para não bater no INSERT desnecessariamente. Não é estritamente necessário (a UNIQUE pega), mas é barato.

**Critério de aceitação:**
- [ ] `handleUpdateGrindSession` com `req.body.status='completed'` para um user com `reportDailyEnabled=true` (tier elegível) → enfileira 1 `report_jobs` row `report_type='daily'`, `period_start = data da sessão (fuso do user)`, `period_end = mesma data`, `status='pending'`, `enqueued_by='session_completed'`; a resposta do PUT **não atrasa** (o enqueue é best-effort, não bloqueante) e **não falha** se o enqueue der erro (try/catch — lesson #9).
- [ ] User com `reportDailyEnabled=false` ou Free → finalizar sessão não enfileira daily job.
- [ ] Finalizar 2 sessões no mesmo dia (mesmo user) → no máximo 1 daily `report_jobs` row (UNIQUE); o gerador agrega as sessões do dia (verificável: o `content` reflete N sessões).
- [ ] `generateDailyDebrief({ userId, periodStart, injectedStorage? })` (ou variante de `generateReport`) com uma sessão com dados → retorna `{ content, markdown, status:'ready', model, usage }`; `content` tem o cabeçalho + resultado da sessão + spots + comparação + feedback (≥1 item com `citations.length>=1`); custo > 0; `cost_usd_estimate` gravado.
- [ ] Daily debrief usa `session_tournaments` da(s) sessão(ões) do dia (NÃO o histórico `tournaments`) para os números da sessão; FX normalizado para USD antes de comparar (lesson #6).
- [ ] CTAs do daily só referenciam tools que existem (AI-0A) ou rotas Wouter registradas (lesson #19) — nunca `bulk_propose_grade`/`schedule_study_block`/`define_career_goal`/`mark_off_day`.
- [ ] Sessão com 0 torneios e 0 spots → daily `status='ready'`, `dataSufficiency='low'`, header minimalista, custo ≈ 0, sem chamar o LLM pra prosa.
- [ ] Sem `ANTHROPIC_API_KEY` → daily `status='degraded'`, `degraded_reason='no_anthropic_key'`, números completos, sem prosa, job `done` na 1ª tentativa.
- [ ] LLM falha 3x → daily `status='degraded'`, `degraded_reason='llm_failed_3x'`, job `done` (nunca `failed`); backoff respeitado.
- [ ] O daily aparece na timeline do hub (`GET /api/coach/timeline` retorna o item `kind:'report'` com `reportType='daily'`); `GET /api/coach/reports/:id` renderiza o markdown.
- [ ] (Opcional, se o system-architect optar) um toast pós-finalização no `/grind-live` ("Seu debrief da sessão estará disponível no Coach em alguns minutos") — não bloqueante, não obrigatório.
- [ ] `COACH_NUDGES_ENABLED='false'` → o processor não roda, então o daily job fica `pending` parado; quando volta, processa. (O *enqueue* na finalização da sessão: decisão — o enqueue **continua acontecendo** mesmo com a flag off [o job só não é *processado*], OU o enqueue também respeita a flag. **Recomendação:** o enqueue respeita a flag — se `COACH_NUDGES_ENABLED==='false'`, `enqueueDailyDebriefForSession` é no-op [consistente com "relatórios contam como proatividade"]. System-architect decide; documentar.)

### RF-04: Daily Debrief — gerador (compartilhamento de helpers com o weekly)
**Descrição:** Decisão de estrutura: **generalizar** vs **arquivos separados**. O `weeklyReportGenerator.ts` já tem `gatherBundle`, `buildSections`, `renderMarkdown`, `persistReport`, `runBackfills`, `callLlm`, `buildDeterministic`. O daily precisa de um bundle diferente (sessão do dia, não a semana) e seções diferentes (curtas). **Recomendação:** extrair os helpers compartilháveis (`persistReport` já é genérico — só hardcoda `reportType:'weekly'` que vira parâmetro; `sanitizeHref`/`ALLOWED_HREFS`; `computeCost`; `n`/`safe`/`resolveStorage`; o padrão `callLlm` com `new AnthropicCtor` try/catch) para um módulo `server/services/reportGeneratorShared.ts` (ou `server/coach/reportShared.ts`), e ter `server/services/dailyDebriefGenerator.ts` (`generateDailyDebrief({ userId, periodStart, injectedStorage? })`) + `server/services/monthlyReportGenerator.ts` (RF-05) + `weeklyReportGenerator.ts` reusando os shared. **Alternativa:** um único `generateReport({ reportType, userId, periodStart, periodEnd, ... })` que internamente despacha. System-architect decide; o critério é: **DRY dos helpers** (não duplicar `persistReport`/`callLlm`/`sanitizeHref` — lesson #10 sobre divergência de prompt aplica-se também a divergência de helpers que tocam o `ReportContent`), e o `reportType` deve ser um parâmetro (não hardcodado em `'weekly'` em vários lugares).
- O `processReportJobsTick` do AI-1B hoje chama `import("../services/weeklyReportGenerator").generateWeeklyReport(...)` independente do `report_type` do job. **Mudança necessária:** o processor despacha por `job.reportType` → `'weekly'` → `generateWeeklyReport`; `'daily'` → `generateDailyDebrief`; `'monthly'` → `generateMonthlyReport`. Um pequeno `getGeneratorFor(reportType)` ou `switch`. (`'quarterly'` → AI-2B, não despachado ainda — se vier um job desses, o processor loga `unsupported_report_type` e marca `skipped` ou `done` sem regerar.)
- `persistReport` (e `upsertReport` no `reportStorage.ts`) já aceitam `reportType` como campo da row — confirmar que não está hardcodado em `'weekly'` no caminho de daily/monthly (hoje `upsertReport` faz `reportType: row.reportType ?? "weekly"` — OK, só passar o valor certo).

**Critério de aceitação:**
- [ ] Helpers compartilhados (`persistReport` parametrizado por `reportType`, `sanitizeHref`/`ALLOWED_HREFS`, `computeCost`, `callLlm`-padrão, `resolveStorage`, `n`/`safe`) extraídos para um módulo compartilhado; `weeklyReportGenerator.ts` reusa-os (sem regressão — testes do AI-1B continuam verdes).
- [ ] `processReportJobsTick` despacha o gerador por `job.reportType` (`weekly`/`daily`/`monthly`); `report_type` desconhecido → loga + `skipped` (não quebra o tick).
- [ ] `generateDailyDebrief` e `generateMonthlyReport` aceitam `injectedStorage?` (lesson #34).
- [ ] Nenhum caminho de daily/monthly grava `reportType:'weekly'` por engano no `reports` row.

### RF-05: Monthly Report — schema do job, gatilho (dia 1 7h tz), conteúdo (comparativos + variância + leaks + metas), custo, fail-soft
**Descrição:** Relatório mensal automático. Opt-in (`report_monthly_enabled`), só tier elegível. Mais caro (~$0.11). Sonnet 4.6 + sumarização hierárquica Haiku do contexto (RF-07).

#### RF-05.1 — Gatilho (regra no enqueuer hourly do AI-1B)
- **Onde:** adicionar uma regra ao `enqueueWeeklyReportJobsTick` (ou um tick irmão `enqueueMonthlyReportJobsTick` chamado no mesmo cron `0 * * * *`; system-architect decide — recomendação: estender o enqueuer existente, ele já itera os users e checa fuso). Para cada user elegível com `reportMonthlyEnabled=true`: se, **no fuso do user**, hoje é o **dia 1 do mês E a hora local é 7** (`getLocalHour(now, tz) === 7` && `civilDay === 1`) → calcula `period_start` = o **1º dia do mês anterior** (no fuso do user, formato `YYYY-MM-DD`), `period_end` = o **último dia do mês anterior** → `INSERT INTO report_jobs (...) ON CONFLICT (user_id, 'monthly', period_start) DO NOTHING` com `report_type='monthly'`, `scheduled_for = now`, `status='pending'`, `timezone = user.timezone`, `subscription_plan_at_enqueue = user.subscriptionPlan`, `enqueued_by = 'cron_enqueuer'`.
  - **Idempotência:** UNIQUE `(user_id, 'monthly', period_start)` → 1 monthly job por user por mês. Rodar de hora em hora cobre todos os fusos com granularidade de 1h (mesmo padrão do weekly).
  - **Por que dia 1 e não fim do mês:** o relatório cobre o **mês que acabou** (entregue no dia 1 do mês seguinte às 7h). `period_start` = 1º dia do mês passado; `period_end` = último dia do mês passado. (Ex: enfileira dia 01/jun 7h → cobre 01/mai–31/mai.)
- O processor processa o job (a cada 15min) → despacha para `generateMonthlyReport` (RF-04) → cria o `reports` row `report_type='monthly'` → marca o job `done`.

### RF-07: Sumarização hierárquica Haiku→Sonnet — camadas, threshold, modelo, uso no gerador
**Descrição:** Formalizar e tornar hierárquica a sumarização de contexto (o AI-1B já tem um "sumariza com Haiku se grande" — hoje stub). Reusa o pattern de `server/coachMemory.ts` (sumarização de memória já usa Haiku via `getMemoryModel()` lendo `COACH_MEMORY_MODEL`, default `'claude-haiku-4-5-20251001'`).
- **Módulo:** `server/coach/hierarchicalSummarizer.ts` (ou `server/services/reportSummarizer.ts`) — função `summarizeBundleHierarchical({ bundle, reportType, model? }): Promise<{ summarizedBundle: any; summarizerModelUsed: string | null; layersUsed: number }>`. Modelo: `process.env.COACH_REPORT_SUMMARIZER_MODEL ?? COACH_MEMORY_MODEL ?? 'claude-haiku-4-5-20251001'` (usar a fonte canônica do projeto — verificar `coachMemory.ts`).
- **Camadas (hierárquico):** para os dados de séries longas (esp. o `last_12_months` do monthly): camada 1 = raw (12 meses de dados granulares) → Haiku resume **por mês** (12 resumos curtos); camada 2 = os 12 resumos/mês → Haiku resume **por trimestre** (4 resumos); camada 3 = os 4 resumos/trimestre → Haiku resume **por ano** (1 resumo). Só o resumo final (ano) + (opcional) os resumos/trimestre + os dados do mês corrente em detalhe vão pro sonnet. Para o **weekly** (bundle menor), normalmente só 1 camada (resume o que passar do threshold) ou nenhuma. Para o **daily** (bundle pequeno), **nunca** aciona.
- **Threshold de tamanho que aciona:** uma estimativa barata do tamanho do bundle (ex: `JSON.stringify(bundle).length` ou uma contagem de tokens aproximada `chars/4`). Se acima de um limite (ex: `> ~20000 chars` ou `> ~5000 tokens` estimados — system-architect calibra; o critério: só sumarizar quando vale a pena economizar input tokens do sonnet, considerando que o prompt caching já cobre o bloco STATIC) → roda a sumarização. Configurável via env opcional `COACH_REPORT_SUMMARIZE_THRESHOLD_CHARS` (default ~20000).
- **Uso no gerador:** o `generateMonthlyReport` (e o `generateWeeklyReport` refatorado), depois de `gatherBundle`, chama `summarizeBundleHierarchical` se o bundle for grande; passa o `summarizedBundle` pro prompt do LLM; grava `summarizer_model_used` no `reports` row. **Fail-soft da sumarização:** se a chamada Haiku falhar (exceção, sem key, mock quebrado — `new AnthropicCtor` try/catch lesson #5/#35) → loga (lesson #9) e usa o bundle **truncado** (corta as séries longas para os últimos N meses, sem chamar o LLM) — não derruba o relatório, só perde detalhe de contexto. `summarizer_model_used = null` nesse caso (não sumarizou de fato).
- **Reaproveitamento:** se `coachMemory.ts` já expõe um helper de "resumir texto com Haiku", reusar a chamada base (não duplicar o `new AnthropicCtor`/parse — lesson #10 aplicada a helpers de LLM); só a estrutura de camadas é nova.

**Critério de aceitação:**
- [ ] `summarizeBundleHierarchical({ bundle: <bundle grande, 12 meses>, reportType:'monthly' })` → roda Haiku em camadas (raw→mês→trimestre→ano para as séries longas), retorna `{ summarizedBundle, summarizerModelUsed: '<haiku model>', layersUsed >= 1 }`; o `summarizedBundle` é menor que o `bundle` original (`JSON.stringify(...).length` menor) e preserva o mês corrente em detalhe.
- [ ] Bundle pequeno (abaixo do threshold) → `summarizeBundleHierarchical` retorna `{ summarizedBundle: bundle, summarizerModelUsed: null, layersUsed: 0 }` (no-op — não chama o LLM).
- [ ] Daily debrief → nunca aciona a sumarização (bundle sempre pequeno); `summarizer_model_used = null` no `reports` row do daily.
- [ ] `generateMonthlyReport` com bundle grande → `reports.summarizer_model_used` preenchido; com bundle pequeno → `null`.
- [ ] Sumarização Haiku falha (mock lança / sem key / `new AnthropicCtor` que é `vi.fn()`) → não quebra o relatório; usa o bundle truncado; `summarizer_model_used = null`; o erro é **logado** antes do fallback (lesson #9).
- [ ] Threshold configurável via `COACH_REPORT_SUMMARIZE_THRESHOLD_CHARS` (default ~20000); abaixo → não sumariza, acima → sumariza.
- [ ] O `weeklyReportGenerator.ts` (refatorado) usa o mesmo `summarizeBundleHierarchical` (substitui o stub "sumariza com Haiku se grande" do AI-1B); testes do AI-1B continuam verdes.

### RF-08: Follow-ups inteligentes — seção "Seu acompanhamento" nos relatórios + bloco "follow-ups abertos" no contexto do chat + o agente mencionando
**Descrição:** O agente lembra do que sugeriu e fecha o loop. 3 frentes:

#### RF-08.1 — Seção "Seu acompanhamento" nos relatórios (weekly + monthly + daily)

### RF-09: Tool batching — `bulk_query_dimensions`
**Descrição:** Tool nova `bulk_query_dimensions` — em vez de N chamadas sequenciais de `query_dimension` (AI-0A), uma chamada com um array de specs. Generalizada a partir de `server/coachTools/handlers/queryDimension.ts`.
- **Localização:** `server/coachTools/handlers/bulkQueryDimensions.ts`. Registrada no registry via `server/coachTools/index.ts` (`safeRegister(bulkQueryDimensionsTool)` + export + entrada em `coachTools[]` — lesson #8: testes validam presença individual, nunca length absoluta).
- **Input schema (zod):** `{ queries: Array<{ id?: string; dimension: <enum query_dimension>; groupBy?: <enum>; filters?: <mesmo de query_dimension>; period?: <enum> }> }` — `queries` com no máximo N specs (ex: `max(8)` — defesa contra abuso; system-architect calibra). Reaproveita o `queryDimensionInputSchema` (cada item é um `QueryDimensionInput` opcionalmente com `id` pra correlação).
- **Output:** `{ results: Array<{ id?: string; dimension; groupBy; rows; totalCount; period; note? } | { id?: string; ok: false; error: string }> }` — um resultado por spec, na mesma ordem; cada resultado tem o mesmo shape de `query_dimension` (ou um `{ ok:false, error }` por-item se aquela spec falhar — uma spec ruim não derruba as outras). **Reaproveita o `handler` de `query_dimension`** (extrair a lógica interna `runQueryDimension(input, ctx)` de `queryDimension.ts` para uma função reutilizável; `query_dimension` e `bulk_query_dimensions` ambos chamam — DRY). Execução: pode ser sequencial (com pacing, se houver risco de pressão no DB) ou `Promise.all` (analytics são reads, geralmente OK) — system-architect decide; o critério: 1 chamada de tool em vez de N, e robusta a uma spec ruim.
- **Metadados da tool:** `requiresConfirmation: false` (read tool — nenhum side-effect); `auditLevel: 'log'` (mesmo de `query_dimension`); `gateByTier: ['pro','premium','admin']` (mesma lógica de tier gating do `query_dimension` — o registry filtra por `gateByTier`; free → tool não aparece). **Atenção:** o roadmap diz "nível `none`" — mas `query_dimension` usa `'log'` e o `auditLevel` é `'none'|'log'|'persist'` (não `'read'`); "nível none" no roadmap parece referir-se a "não requer confirmação" (`requiresConfirmation: false`) — manter `auditLevel: 'log'` por consistência com `query_dimension` (logar a invocação é útil pra telemetria; não persiste nada — `'log'` ≠ `'persist'`). System-architect confirma; o critério mínimo: `requiresConfirmation: false`, gateado por tier igual ao `query_dimension`.
- O `description` da tool deixa claro: "Roda VÁRIAS consultas de dimensão numa chamada só — passe um array de specs (até N). Use isto em vez de chamar query_dimension N vezes seguidas." (incentiva o LLM a batchar.)

**Critério de aceitação:**
- [ ] `bulkQueryDimensionsTool` está registrada no registry (`coachTools` inclui ela; `getTool('bulk_query_dimensions')` retorna a tool); exportada de `server/coachTools/index.ts`.
- [ ] Input com `{ queries: [{ dimension:'roi', groupBy:'site' }, { dimension:'volume', period:'90d' }] }` → output `{ results: [<resultado roi by site>, <resultado volume 90d>] }` na mesma ordem; cada resultado com o shape de `query_dimension` (`rows`/`totalCount`/`period`).
- [ ] Uma spec inválida no array (ex `{ dimension:'xpto' }`) → aquele resultado é `{ ok:false, error:'validation_failed', ... }` mas as outras specs retornam normalmente (não derruba a chamada inteira).
- [ ] DB explode numa spec → aquele resultado é `{ ok:false, error:'handler_error', ... }` (logado antes — lesson #9); as outras seguem.
- [ ] `queries` acima do limite (ex 20 specs com max 8) → 400/`validation_failed` (ou trunca pras primeiras 8 — system-architect decide; o critério: não aceitar arrays absurdos).
- [ ] `requiresConfirmation: false`; `gateByTier` igual ao `query_dimension` (`['pro','premium','admin']`) — free não vê a tool (o registry filtra por `gateByTier`).
- [ ] A lógica interna de `query_dimension` foi extraída para uma função reutilizável (`runQueryDimension`); `query_dimension` e `bulk_query_dimensions` ambos a usam (DRY — sem regressão no `query_dimension`, testes do AI-0A verdes).

## Requisitos Não-Funcionais
- **Custo de tokens:**
  - **Daily Debrief** — ~$0.013/debrief (sonnet 4.6, `max_tokens` ~1200, prompt caching no bloco STATIC). Barato mas **frequente** → cap **1/dia por user** (UNIQUE `(user_id,'daily',period_start=data)`); o gerador agrega as sessões do dia, nunca gera 2 dailies/dia. Custo + tokens gravados em cada `reports` row.
  - **Monthly Report** — ~$0.11/relatório (sonnet 4.6, `max_tokens` ~4000) + a sumarização Haiku do contexto quando o bundle é grande (Haiku é ~10× mais barato — economiza input tokens do sonnet). 1/mês por user. Custo + tokens + `summarizer_model_used` gravados.
  - **Sumarização** sempre Haiku (`COACH_REPORT_SUMMARIZER_MODEL ?? COACH_MEMORY_MODEL ?? 'claude-haiku-4-5-...'`); só aciona acima do threshold; fail-soft pra bundle truncado (não chama LLM).
  - Fail-soft e `dataSufficiency='low'` → custo ≈ $0 (não chama o sonnet).
  - Logar `coach.report.tokens` com `inputTokens/cacheCreation/cacheRead/outputTokens` (visibilidade de cache hit/miss) — padrão do AI-1B.
- **Daily não atrasa o finalizar da sessão:** o enqueue em `handleUpdateGrindSession` é **best-effort, não-bloqueante** (try/catch que nunca lança; fire-and-forget ou um `await` que só faz 1 INSERT rápido; a resposta do PUT sai imediatamente). **Não gera o relatório síncrono** — só enfileira; o processor (já existente, a cada 15min) gera depois.
- **Idempotência:** `report_jobs` UNIQUE `(user_id, report_type, period_start)` (cobre weekly/daily/monthly); `reports` UNIQUE idem; `coach_lesson_recommendations`/`study_weekly_plans` mantêm suas UNIQUEs (o `runBackfills` é idempotente). Nenhum caminho duplica relatório.
- **Timezone:** "dia 1 7h" (monthly) e "data da sessão" (daily — `completedAt` no fuso do user) usam o helper de fuso (`getLocalHour` / `localCivilDate` — já existem em `reportJobRunner.ts`). Testar fusos extremos (UTC+14, UTC-11) e meses de borda (jan↔dez, fevereiro, mês 31 dias). `report_jobs.timezone` é o snapshot do `users.timezone` no enfileiramento.
- **Comparativos mensais corretos:** a agregação por mês (`getMonthlyPerformanceSeries` se criado, ou a composição via `getPerformanceByPeriod` por mês) deve respeitar boundaries de mês e timezone — **testar** com `now` controlado. Risco: comparativo errado se a agregação bugar.
- **Tier gating estrito (não regredir):** `getReportTier` é a fonte canônica; o enqueuer e o processor (revalidação) usam ela; Free nunca recebe; Trial agora recebe; o `PRO_PLANS` cru do AI-1B foi corrigido. Downgrade entre enfileirar e processar → `skipped` (já tratado no AI-1B, atualizado pra usar `getReportTier`).
- **Concorrência (réplicas):** os ticks do report job runner já estão em `withAdvisoryLock` (ADR-144); o claim de job é atômico. As mudanças deste sprint (despacho por `report_type`, enqueue do daily) não introduzem race nova — o INSERT do daily é `ON CONFLICT DO NOTHING`.
- **Fail-soft / robustez:** erros do LLM (sonnet ou Haiku) nunca propagam pra fora do gerador (lesson #9 — logar e cair pro determinístico/truncado). `new AnthropicCtor` em try/catch com fallback factory (lesson #5/#35). Erros de storage em qualquer check de elegibilidade → safe-deny. `try/catch` por user no enqueuer (lesson #9). O enqueue do daily em `handleUpdateGrindSession` nunca quebra a resposta do PUT.
- **Gating de ativação:** os crons só rodam em `NODE_ENV === 'production' || COACH_CRON_ENABLED === 'true'` (igual aos outros). `COACH_NUDGES_ENABLED='false'` é o kill switch global — desliga o report job runner (enqueuer + processor) e (recomendado) o enqueue do daily na finalização da sessão.
- **Performance:** o processor pega no máximo 25 jobs/tick (paginação — AI-1B), pacing 200ms entre jobs; daily/monthly entram nessa fila como qualquer job. A sumarização Haiku adiciona latência ao monthly (~1-3 chamadas Haiku) — aceitável (é um job assíncrono, não um request do usuário). `bulk_query_dimensions` limita a N specs por chamada. Queries do gerador filtram `grind_session_id IS NULL` (§6.1 — exceto o daily que usa `session_tournaments` da sessão).
- **Segurança:** `requireAuth` nos endpoints (timeline/reports já têm — AI-1B); ownership 404/403 nos reports; `injectedStorage?` nos handlers/geradores (lesson #34); zod `.strict()` no `updateCoachPreferencesSchema`; `bulk_query_dimensions` valida cada spec via zod (LLM pode mandar shape ruim).
- **Compatibilidade:** o `weeklyReportGenerator.ts` é refatorado (helpers compartilhados, usa `summarizeBundleHierarchical`) — **sem regressão** (testes do AI-1B verdes). O `processReportJobsTick` ganha despacho por `report_type` (`'weekly'` → comportamento atual). O `ReportContent` ganha campos opcionais + `schemaVersion: 2` (frontend tolera 1 e 2 — lesson #7). O `query_dimension` tem a lógica extraída pra `runQueryDimension` (mesmo comportamento). O frontend de `/inicio` (`CoachRecommendationCard` etc.) e o `StudyWeeklyPlanCard` não mudam (o `runBackfills` continua preenchendo `coach_lesson_recommendations`/`study_weekly_plans` — agora também no daily/monthly? **Decisão:** o `runBackfills` (rec de lesson + plano de estudo) roda no **weekly** e no **monthly** [ambos cobrem ≥1 semana], **não** no daily [o daily é por sessão, não por semana — não faz sentido regerar a rec de lesson semanal a cada sessão; e o daily roda múltiplas vezes/semana, regerar seria desperdício]). Os toggles novos na UI de Preferências (3 toggles: weekly/daily/monthly) — o `CoachPreferencesPanel` ganha 2 toggles.

## Cenários de Teste Derivados

### Happy Path
- [ ] Jogador finaliza uma sessão de grind (`PUT /api/grind-sessions/:id { status:'completed' }`) com `reportDailyEnabled=true` (tier elegível) → 1 `report_jobs` row `report_type='daily'`, `period_start = data da sessão`, `status='pending'`; a resposta do PUT sai imediatamente; processor (≤15min) → `generateDailyDebrief` (LLM mockado) → `reports` row `status='ready'` com `sessionSummary` + feedback + (se houver) `followUp`, job `done` com `report_id`; o daily aparece em `GET /api/coach/timeline` (`kind:'report'`, `reportType='daily'`); abrir → `ReportView` renderiza o resumo da sessão.
- [ ] Enqueuer hourly com `now` = dia 1 do mês 07:xx (fuso de um user `trial` com `reportMonthlyEnabled=true`) → 1 `report_jobs` row `report_type='monthly'`, `period_start = 1º dia do mês anterior`; processor → `generateMonthlyReport` (LLM mockado, bundle grande → Haiku sumariza) → `reports` row `status='ready'` com as 5 seções + `comparatives` (mês -1 / 6m / 12m) + `variance` (heurística) + `leaksDelta` + `goalsProgress` + `insights` (3-5) + `followUp`, `summarizer_model_used` preenchido, job `done`; aparece na timeline (`reportType='monthly'`); `runBackfills` também criou/UPSERTou `coach_lesson_recommendations` + `study_weekly_plans`.
- [ ] LLM (no chat) faz uma `bulk_query_dimensions` com 3 specs → 1 chamada de tool retorna 3 resultados na ordem (em vez de 3 chamadas de `query_dimension`).
- [ ] Relatório (weekly/monthly/daily) com foco de leak ativo + meta em progresso → seção "Seu acompanhamento" renderizada; o chat tem um bloco `## Follow-ups abertos` no contexto dinâmico; o agente menciona o follow-up quando relevante.

### Validação de Input
- [ ] `PUT /api/coach/preferences { reportDailyEnabled: true, reportMonthlyEnabled: false }` → aceito (zod `.strict()`); GET reflete os 3 toggles (weekly/daily/monthly).
- [ ] `PUT /api/coach/preferences { frozenCategories: {...} }` → 400 (`.strict()` rejeita campo cru — comportamento AI-1A mantido).
- [ ] `bulk_query_dimensions` com uma spec inválida no array → aquele resultado é `{ ok:false, error:'validation_failed' }`, as outras retornam normalmente.
- [ ] `bulk_query_dimensions` com `queries` acima do limite → `validation_failed` (ou trunca — conforme decisão); arrays absurdos não são aceitos.
- [ ] `GET /api/coach/reports/:id` (daily ou monthly) com id inexistente → 404; de outro user → 403.

### Regras de Negócio
- [ ] User Free → finalizar sessão **não** enfileira daily job; enqueuer **não** cria monthly job pra ele; os toggles de daily/monthly **não aparecem** na UI de Preferências; setar `true` via API direta → o enqueuer/processor revalida `getReportTier` → não enfileira / `skipped`.
- [ ] User `trial` com `reportWeeklyEnabled=true` → agora recebe o Weekly Report (antes não recebia por causa do `PRO_PLANS` bug do AI-1B — corrigido). User `trial` com `reportDailyEnabled=true` → recebe o daily ao finalizar sessão. User `trial` com `reportMonthlyEnabled=true` → recebe o monthly dia 1.
- [ ] User Pro+ que faz downgrade para Free entre enfileirar (daily/monthly) e processar → o job vira `skipped` (`last_error='no_longer_eligible'`), nenhum `reports` row.
- [ ] Finalizar 2 sessões no mesmo dia (mesmo user, opt-in) → no máximo 1 daily `report_jobs` row e 1 daily `reports` row; o `content` reflete as sessões do dia (agregadas).
- [ ] `runBackfills` (rec de lesson + plano de estudo) roda no weekly e no monthly, **não** no daily; `GET /api/home/coach-recommendation` continua funcionando após weekly/monthly rodar; `StudyWeeklyPlanCard` idem.
- [ ] CTAs de daily/monthly só referenciam tools que existem (AI-0A) ou rotas Wouter registradas — nunca `bulk_propose_grade`/`schedule_study_block`/`define_career_goal`/`mark_off_day`.
- [ ] Daily debrief usa `session_tournaments` da sessão (não o histórico `tournaments`); monthly usa o histórico (`grind_session_id IS NULL`) — verificável via os métodos chamados.
- [ ] `processReportJobsTick` despacha por `report_type`: `'weekly'`→`generateWeeklyReport`, `'daily'`→`generateDailyDebrief`, `'monthly'`→`generateMonthlyReport`; um `report_type` desconhecido (ex `'quarterly'`) → loga + `skipped` (não quebra o tick).

### Edge Cases
- [ ] Fusos extremos: enqueuer (rodando em UTC) cria o monthly job pro user `Pacific/Kiritimati` (UTC+14) quando é dia 1 7h **lá** e pro user `America/Sao_Paulo` quando é dia 1 7h **lá**, sem pular nem duplicar; meses de borda (jan↔dez — `period_start` = 01/12 do ano anterior; fevereiro 28/29; mês com 31 dias) → `period_start`/`period_end` corretos; `comparatives` não pega mês errado.
- [ ] Daily debrief: sessão com 0 torneios e 0 spots → `status='ready'`, `dataSufficiency='low'`, header minimalista, custo ≈ 0, LLM não chamado pra prosa.
- [ ] Monthly: mês sem dados (user novo) → `status='ready'`, `dataSufficiency='low'`, header convidando a importar, CTA `/upload`, custo ≈ 0.
- [ ] Sem `ANTHROPIC_API_KEY` → daily/monthly `status='degraded'` (`degraded_reason='no_anthropic_key'`), números/comparativos completos, sem prosa, job `done` na 1ª tentativa.
- [ ] LLM falha 3x (daily ou monthly) → `status='degraded'` (`degraded_reason='llm_failed_3x'`), job `done` (nunca `failed`), backoff respeitado entre tentativas (`next_attempt_at`).
- [ ] `new AnthropicCtor` que é um `vi.fn()` mock (sonnet **ou** Haiku) → não quebra; cai pro determinístico (relatório) ou pro bundle truncado (sumarização) (lesson #5/#35).
- [ ] Sumarização Haiku falha (mock lança) → o monthly **não** quebra; usa o bundle truncado; `summarizer_model_used = null`; erro logado antes do fallback (lesson #9).
- [ ] Bundle pequeno (weekly de semana fraca) → `summarizeBundleHierarchical` é no-op (não chama Haiku); `summarizer_model_used = null`.
- [ ] O enqueue do daily em `handleUpdateGrindSession` lança um erro interno (storage off) → a resposta do PUT **ainda sai 200** (try/catch, best-effort — lesson #9).
- [ ] `COACH_NUDGES_ENABLED='false'` → enqueuer (weekly+monthly), processor não fazem trabalho; o enqueue do daily na finalização da sessão também é no-op (recomendado); jobs já enfileirados ficam parados; quando volta, o processor pega os atrasados (`scheduled_for <= now` ainda vale).
- [ ] Relatório sem foco de leak ativo e sem metas → `followUp` ausente; o `ReportView` não renderiza a seção "Seu acompanhamento"; o `coachContext.ts` não adiciona o bloco `## Follow-ups abertos`.
- [ ] 2 réplicas processando concorrentemente → o mesmo daily/monthly job não é processado 2x (claim atômico — AI-1B); 2 enqueuers concorrentes → 1 monthly job só (`ON CONFLICT DO NOTHING`).

- **ADR-159** — AI-1C: Daily Debrief (enqueue event-driven pós-`session.completed` em `handleUpdateGrindSession`, best-effort não-bloqueante, processado pelo job runner do AI-1B; usa `session_tournaments` da sessão; cap 1/dia agregando sessões; `report_type='daily'`, `period_start` = data da sessão) + Monthly Report (regra dia 1 7h tz no enqueuer hourly; `report_type='monthly'`, `period_start` = 1º dia do mês anterior; comparativos vs mês -1/6m/12m; variância heurística [`variance.method='heuristic'`, `'primedope'` quando disponível]; leaks resolvidos/novos via `coach_leak_focus`+`detectLeaks`; progresso das metas do perfil estruturado) + tier gating estrito (`getReportTier` inclui Trial; corrige o `PRO_PLANS`/`subscription_plan IN ('pro','premium')` bug latente do AI-1B — relatórios elegem por tier resolvido, não por `users.subscription_plan` cru; downgrade → `skipped`) + sumarização hierárquica Haiku→Sonnet (camadas raw→mês→trimestre→ano para séries longas, threshold de tamanho `COACH_REPORT_SUMMARIZE_THRESHOLD_CHARS`, fail-soft pra bundle truncado; reusa o pattern de `coachMemory.ts`) + generalização dos geradores (helpers compartilhados, `processReportJobsTick` despacha por `report_type`).
